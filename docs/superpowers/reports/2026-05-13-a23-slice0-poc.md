## Key API findings (spec adjustments)

The spec's pseudocode said:

```rust
let response: ForwardInputsResult = model.forward(request).await?;
match response { ForwardInputsResult::RawLogits { logits } => ... }
```

That's wrong shape. **`ForwardInputsResult` is NOT publicly re-exported from
the `mistralrs` crate** (it lives only in `mistralrs-core`, which the public
API of `mistralrs` doesn't re-export). Instead, the canonical pattern (lifted
from `mistralrs/examples/advanced/perplexity/main.rs`) is:

```rust
use mistralrs::{
    cross_entropy_loss, parse_isq_value, Constraint, DType, Device, MistralRs,
    ModelBuilder, NormalRequest, Request, RequestMessage, ResponseOk,
    SamplingParams, Tensor,
};
use tokio::sync::mpsc::channel;

let model = ModelBuilder::new(model_id).build().await?;
let inner = model.inner();  // returns &Arc<MistralRs>, the runtime

let tokens = model.tokenize(plaintext, None, false, false, None).await?;
let bos_token = model.tokenize(" ", None, true, false, None).await?[0];

let (tx, mut rx) = channel(1);
let request = Request::Normal(Box::new(NormalRequest {
    messages: RequestMessage::CompletionTokens(tokens),
    sampling_params: SamplingParams {
        max_len: Some(0),
        ..SamplingParams::deterministic()
    },
    response: tx,
    return_logprobs: false,
    is_streaming: false,
    id: 0,
    constraint: Constraint::None,
    suffix: None,
    tools: None,
    tool_choice: None,
    logits_processors: None,
    return_raw_logits: true,
    web_search_options: None,
    max_tool_rounds: None,
    tool_dispatch_url: None,
    model_id: None,
    truncate_sequence: false,
}));
inner.get_sender(None)?.send(request).await?;

let response = rx.recv().await.context("channel closed")?.as_result()?;
let ResponseOk::Raw { logits_chunks, tokens } = response else {
    anyhow::bail!("expected Raw response");
};
// logits_chunks[0] is the Tensor of shape [seq_len, vocab]
// Compute cross_entropy_loss(logits, tokens) or roll your own log_softmax + gather.
```

mistralrs's perplexity example uses `cross_entropy_loss` directly (also
re-exported from `mistralrs`) so we don't need to write the aggregation
logic ourselves. Our `aggregate_perplexity_metrics` helper can stay for
the tail-fraction computation but the headline perplexity can flow
through `cross_entropy_loss`.

## Plan adjustments

The A2.3 plan's Slice 2 needs the corrected pseudocode. Specifically:

1. **Drop the `ForwardInputsResult::RawLogits` match.** Replace with
   `Request::Normal` + channel-based `ResponseOk::Raw` destructure.
2. **`MistralRs` is the runtime; `Model` is the wrapper.** The scorer
   holds `Mutex<Model>` (not `TextModel` as the plan had it). Use
   `model.inner()` to get `&Arc<MistralRs>` for sending requests.
3. **Tokenization is async too** — `model.tokenize(...).await`. The
   owned-runtime pattern in the plan still works for bridging to the
   sync `PerplexityScorer::score` trait method.
4. **`cross_entropy_loss` is re-exported** — perplexity aggregation can
   reuse mistralrs's helper instead of our own log_softmax + gather.

These are small adjustments. The plan's slice structure (5 commits,
Slice 0 hard gate, owned runtime, drop direct candle deps) all stay.

## Additional findings (informational)

- **mistralrs implements Gemma 4 in `mistralrs-core` directly,** not via
  candle's `models::gemma4`. So mistralrs + candle 0.10.2 (crates.io
  release that pre-dates candle's `gemma4.rs` on main) supports Gemma 4
  fine. The A2.2 candle-main git-pin (`5447a87`) becomes unnecessary
  after A2.3 lands — drop it in favor of mistralrs's transitive 0.10.2
  pin, exactly as the plan recommends.
- **Gemma 4 E4B loaded fine** without `HF_TOKEN` set (`Could not load
  token at "/home/ubuntu/.cache/huggingface/token", using no HF token`
  in the log, followed by successful weight download). Confirms the
  no-gating story for Gemma 4.
- **Ubuntu 22.04 build environment** required the same `isoc23` shim
  + `gcc-12` install we documented as smoke-deploy gotchas. The
  `RUSTFLAGS="-L $HOME/isoc23-shim -l static=isoc23shim"` pattern works
  for mistralrs the same way it worked for the original gate binary.
- **Pipeline auto-detection works.** mistralrs read Gemma 4's
  `config.json`, recognized `model_type: gemma4`, and selected the
  multimodal pipeline automatically. No `arch:` parameter needed at the
  call site — confirms the spec's "delete `BackendArch`" decision.
- **Perplexity sample value** (21442.01) was a single number for an
  out-of-distribution short pangram input. Not a calibration data
  point; just confirms the metric path runs. Real bake-off numbers
  will be much lower for in-distribution text.
