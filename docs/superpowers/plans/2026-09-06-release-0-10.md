# Release 0.10.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **For the maintainer:** every RECOMMENDATION below is a default ruling, not a
> decision already taken. Each one is called out with its alternative and the
> reason it was not chosen. Overriding any of them changes only the steps under
> that task; nothing later in the plan depends on which way a ruling goes except
> where the text says so explicitly.

**Goal:** Cut 0.10.0 — the release in which private inference becomes reachable
from all three shells, the consent gate's sentences become Rust-owned, and the
attested-inference path is run end to end for the first time on real traffic.

**Architecture:** Eight gates in dependency order, with a verification-only gate
in front. The shape is inherited from the 0.9.0 release plan: land the code,
establish CI truth, deal with what only fails at tag time, and treat every
operational reading as a *read-back of live state* rather than an assumption
that a written setting took effect. Two things differ from 0.9.0. First, the
live end-to-end leg (Task 3) runs **before** the release rather than after, so
the release notes can say what actually happened instead of what is expected to.
Second, the release carries a real behaviour change on macOS and a real local
exposure on all three platforms, so the release notes are a gate of their own
(Task 7) and not a formality.

**Tech Stack:** Rust (workspace + separate GTK workspace), Swift/SwiftUI,
WinUI/C#, GTK4, Flatpak, dstack/Phala TDX, GitHub Actions, PostgreSQL,
Homebrew, winget.

**Spec:** This release has no design spec of its own. Its specification is the
pair of documents that already describe what a release here involves and what
the attested path claims:

- `docs/superpowers/plans/2026-09-04-attested-inference-release.md` — the 0.9.0
  release plan. Authoritative for release *mechanics*: the two tag series, the
  artifact set, the flatpak vendored-source trap, the Homebrew step, and the
  witness deploy/read-back dance.
- `docs/operator/attested-inference.md` — the enablement runbook. Authoritative
  for the *procedure* in Tasks 3 and 4: the three switches, the four ingest
  variables, the measurement-pinning contract, the stale-container trap, and
  the client-side refusal labels.

Where this plan and either of those disagree, they are right and this plan is
stale — except where this plan says a value moved, in which case re-read it from
the live instance and correct both.

## Global Constraints

- Verification uses `RUSTFLAGS='-D warnings'`. Plain `cargo check` does not
  apply it; CI does.
- `cargo --workspace` misses two configurations that CI gates. Both broke CI on
  2026-09-04. Always also run: the four permissive crates with
  `--no-default-features`, and the GTK workspace with
  `--manifest-path crates/trace-commons-contributor-gtk/Cargo.toml`.
- Clippy allow-list, verbatim: `-A clippy::type_complexity
  -A clippy::collapsible_if -A clippy::manual_option_as_slice
  -A clippy::useless_vec -A clippy::redundant_pattern_matching`. Do not widen
  it.
- No emojis in commits, PRs, code, or reports. Commit subjects are short and
  imperative with no `feat:`/`fix:` prefix.
- Hash-only logging. Never log raw URLs, tokens, bodies, contributor identity,
  or trace content.
- License boundary: `-protocol`, `-contributor`, `-contributor-ffi`,
  `-attestation` are MIT OR Apache-2.0; `-server` and the gate crates are
  AGPL-3.0-or-later. Permissive may flow into AGPL, never the reverse. Never
  edit the expected sets in
  `crates/trace-commons-server/tests/license_boundary.rs`.
- Add no new dependencies. A new dependency invalidates
  `crates/trace-commons-contributor-gtk/flatpak/cargo-sources.json`, which
  nothing in PR CI validates — the first failure is the `linux-flatpak` job on
  an `app-v*` tag.
- The C ABI header exists in two copies that CI requires to be byte-identical:
  `crates/trace-commons-contributor-ffi/include/trace_commons.h` and
  `macos/Sources/CTraceCommons/include/trace_commons.h`.
- Both root and GTK CI now build `--locked` (#661), and the app release builds
  do too (#663). A lockfile that is not committed in step with a manifest is a
  CI failure, not a silent re-resolve. This is load-bearing for Task 2: the
  IronClaw rollback lives **only** in the two lockfiles, because upstream
  IronWire still names `branch = main` for it.
- **The shipped UI is forbidden from repeating the feature's internal name as a
  promise.** `crates/trace-commons-contributor/src/private_inference_copy.rs:22`
  states it: turning `private_inference` on does not make a contributor's calls
  private, and the surface must not say it does. Release notes and any
  contributor-facing prose are bound by the same rule. Describe what it does —
  the daemon runs a local inference proxy — never "private".
- Current versions: both workspaces at `0.9.0`
  (`crates/trace-commons-contributor/Cargo.toml:3`,
  `crates/trace-commons-contributor-ffi/Cargo.toml:3`,
  `crates/trace-commons-contributor-gtk/Cargo.toml:14`). Latest tags
  `app-v0.9.0` and `contributor-v0.9.0`, both at commit `0423b907`.
- Live witness CVM: `8b8e6543-9743-41fc-ac05-a6b414888d5e`, app
  `f1654b0beac2ac2afae4235ee3d907096cd8f3de`, signing address
  `0x655a17fcf6d0b9069e1b1dd07a7f5535d0c76798`. The current measurement is
  **not** reproduced here on purpose — `deploy/witness/README.md`, "The
  production deployment", is the living source, and Task 4 moves it.

- [ ] **Step 3: Cut the upstream release**

RECOMMENDATION: tag it. We control the repository, the alternative is a bare
40-character revision inside a shipped daemon, and a revision pin cannot be
audited by anyone who does not already have a checkout. A tag gives the release
notes, the SBOM conversation and any downstream security question one name to
resolve.

```bash
gh release create v0.1.0 \
  --repo nearai/ironwire \
  --target d1c21c1c490547da36c88e2f4d212f9419c74fa3 \
  --title "ironwire v0.1.0" \
  --notes "The revision TraceCommons 0.10.0 embeds. Tagged so a shipped daemon names a release rather than a bare revision."
```

Then, in this repo, leave `Cargo.toml` pinned to the **revision**, not the tag.
A `rev` is immutable; a `tag` can be moved. The tag is documentation of which
revision, not the mechanism for selecting it. Say so in the release notes.

Overridable: shipping the bare rev pin is the alternative and it works — nothing
breaks. It was rejected only for auditability. If the maintainer would rather
not create a version number on a repository they do not own outright, skip this
step and say "IronWire is pinned to revision `d1c21c1c`" in the release notes
instead.

- [ ] **Step 4: Rule on the IronClaw rollback**


Expected: `ahead` in the region of `259`, `behind` `0` — the pinned revision is

- [ ] **Step 4: Start the local proxy with body capture on**

Two ways in, and they are genuinely different:

*Daemon-hosted (new in this release).* Turn the switch on and let the daemon run
IronWire in-process:

```bash
./target/release/trace-commons-contributor daemon settings --set private_inference=true
./target/release/trace-commons-contributor daemon status
```

The `private_inference_state` object in the status payload carries `state` and
`port`. Expected `state`: `running`. `running_no_backends` means the proxy came
up with an empty backend registry and nothing will ever route through it —
configure a backend in the IronWire home (`$IRONWIRE_HOME`, else `~/.ironwire`)
first.

*Externally hosted.* Run `ironwire` yourself and declare it, in which case the
daemon leaves it alone (`running_elsewhere`).

Either way, **`capture.bodies` is IronWire's own setting and the daemon does not
set it.** In the IronWire home's config:

```toml
[capture]
enabled = true
bodies = true
```

With `bodies` on, IronWire holds complete prompts and completions on local disk,
one exchange per session, rolling. That is a real exposure and the reason this
is not a default.

- [ ] **Step 5: Turn on the switch that sends bodies off the machine**

```bash
./target/release/trace-commons-contributor daemon settings --set ironwire_attested_bodies=true
```

There is no dedicated subcommand; `daemon settings --set KEY=VALUE` is the whole
surface, and `commands::daemon_settings` parses `true`/`false` into a JSON bool
before sending `set_settings`. This is the consequential switch: `ironwire`
declares a proxy to read metadata from, `private_inference` starts one, and
**this** one sends a call's content to the witness.

- [ ] **Step 6: Pin the witness and the receipt endpoint, all together**

Three witness variables are required as a set
(`crates/trace-commons-contributor/src/config.rs:199-219`); a URL with no
address or no measurements is a refusal to configure, not a partial witness.
Note the client separates measurement *sets* with `;` where the server's list is
comma-separated.

```bash
export TRACE_COMMONS_WITNESS_URL='https://f1654b0beac2ac2afae4235ee3d907096cd8f3de-8088.dstack-pha-prod9.phala.network'
export TRACE_COMMONS_WITNESS_SIGNING_ADDRESS='<from step 3>'
export TRACE_COMMONS_WITNESS_EXPECTED_MEASUREMENTS='<measurement from step 3>'
export TRACE_COMMONS_INFERENCE_RECEIPT_ENDPOINT='<the NEAR AI base URL the pilot routes to>'
export TRACE_COMMONS_INFERENCE_RECEIPT_CHECK_ATTESTATION=true
```

`TRACE_COMMONS_INFERENCE_RECEIPT_ENDPOINT` must be an allowlisted HTTPS origin
with no query, fragment or userinfo, or the client refuses it as
`inference_receipt_endpoint_invalid`.
`TRACE_COMMONS_INFERENCE_RECEIPT_CHECK_ATTESTATION` accepts the literal word
`true` and nothing else.

### Task 4: Witness receipt-key pin enablement, in three deployments

Pinning is what makes a receipt mean *an attested NEAR AI enclave signed this*.
Without a pin, verifying a receipt establishes only that a signature checks out
against the key the receipt itself names — which any key satisfies, including
one the submitter holds. The contributor client already compares that key
against an attestation report, but a check the submitter runs on its own
submission is not a bound: a patched client does not run it. The pins are the
same comparison, made where the decision is enforced.

There are **two** pins, and which one a contributor needs is decided by the
protocol their agent speaks, not by the model they call:

| the contributor's inference call | receipt `signature_kind` | signer | pinned by | who this is |
|---|---|---|---|---|
| `POST /v1/chat/completions` | `provider_tee` | the per-model key in `model_attestations` | `TRACE_COMMONS_WITNESS_MODEL_KEY_PINS` | anything driving NEAR AI over chat completions, including any harness still on `wire_api = "chat"` |
| `POST /v1/responses` | `gateway` | the single key in `gateway_attestation` | `TRACE_COMMONS_WITNESS_GATEWAY_RECEIPT_KEY_PINS` | the Codex CLI, which speaks the Responses API exclusively — so **the gateway pin is what makes Codex-driven traffic attestable at all** |

A witness that pins **either** kind refuses the other. Pinning only the model
keys refuses every Codex receipt under the same folded
`witness_inference_receipt_unverified` label as a forgery, which is close to
undiagnosable from outside. This deployment expects both kinds, so it sets both.

**Both kinds are enabled, and the rollout reverses today's production state.**
That is a decision, with its cost accepted; it is recorded once in "Maintainer
decisions, 2026-09-06" at the end of this file and is not re-argued here. Read
that section before starting this task. In particular, the honest statement that
a **gateway-attested exchange proves the request and response bytes and does not
prove which model served them** is stated there, along with the follow-up it
owes. Task 7's notes must not describe a gateway pin as attesting a model.

Overridable, and the alternative is coherent: ship dormant, exactly as 0.9.0
did, and say so. Choosing that still requires **steps 1 through 7**, because
production is pinned today and must be unpinned before 0.10 clients ship; only
steps 8 onwards are skipped, and Task 7's notes then say the pins ship dormant.

- [ ] **Step 8: Derive both key sets from one nonce-bound ed25519 report**

**Do not write a third variant of the derivation here.** The gated `jq`


Three properties in those blocks are load-bearing, and each is a mistake this
deployment has already made once, so they are named here even though the
commands are not:

- **`signing_algo=ed25519` is a required query parameter, not a formatting
  nicety.** It selects which attestations come back, and the default is ECDSA —
  whose signer appears in no ed25519 attestation and signs nothing this witness
  verifies. Omit it and the report looks entirely well formed while containing
  none of the keys you are looking for. That omission is what produced the
  retired variable.
- **A `model_attestations` entry carries no `report_data` field.** Only
  `gateway_attestation` has one, and only as a convenience echo of its own
  quote. On a model attestation the nonce binding is inside `intel_quote`, at
  the TDX quote's `report_data` position — byte offset 568, length 64, hex
  characters `[1136:1264]` — and equals `signing_address` followed by the nonce.
  Filtering on a `.report_data` field matches nothing and yields an empty pin
  list.
- **The header gate is what makes that offset mean anything.** Byte 568 is
  `report_data` only in a v4 TDX quote: hex `[0:4] == "0400"` (version 4, LE)
  and `[8:16] == "81000000"` (TEE type `0x81`, LE). At any other version or TEE
  those bytes are a different field. The witness enforces the same gate, so a
  pin derived without it is one the witness would refuse.

One fetch answers both — a single report carries `gateway_attestation` and
`model_attestations` — so this is two `jq` passes over one response, against one
nonce you chose this minute. The nonce is the whole point: without it you are
pinning a key some report once listed, rather than one attested against a value
you chose.

Cross-check the model key against the server's own drill, which asserts
`receipt_signer_is_attested_key` as its final step:

```bash
curl -sS -X POST -H "authorization: Bearer $ADMIN_JWT" \
  -H 'content-type: application/json' \
  -d '{"purpose":"receipt key pin preflight","record_evidence":true}' \
  "$BASE_INGEST/v1/admin/near-attestation-drill" | jq
```

What this derivation does **not** do, and must not be read as doing: it does not
verify the quote's signature against Intel collateral, and it does not check the
quote's measurements. The strength of the pin is the strength of this one-time
procedure, nothing more.

The two spellings are different and are not interchangeable. Model pins are
`model=key[,model=key...]`; repeat a model to pin more than one key for it,
which is how a model served by several enclaves is pinned. Gateway pins are bare
keys, `key[,key...]`. Both are 64 hex characters with **no `0x`**, and a
`model=` prefix in the gateway variable is refused by name.

In the committed compose rather than as a deploy-time `-e` value, deliberately:
dstack measures an injected variable's **name** but not its value, so a pin
passed at deploy time is not part of the enclave's identity. In the compose it
is — the right place for a public key — and it means rotating a key or adding a
model moves the measurement and needs re-pinning everywhere.

A malformed value — the empty string included — is a **startup failure**, not a
pin that matches nothing. Neither value is echoed into a log: at boot the
process logs `model_key_pins_sha256_prefix` with a `pinned_models` count and
`gateway_key_pins_sha256_prefix` with a `pinned_gateway_keys` count, which is
how an operator confirms which sets it holds without putting a key or a model
name on an operational surface.

## Maintainer decisions, 2026-09-06 (after the first live run)

Decisions, not proposals. The live run reshaped three tasks.

### Both receipt kinds are accepted

NEAR AI chooses the signing key by request PROTOCOL, not by model: Chat
Completions yields `signature_kind: provider_tee`, signed by a per-model
key from `model_attestations`; the Responses API yields `gateway`, signed
by the one shared gateway key. The Codex CLI speaks the Responses API
exclusively, so refusing gateway receipts would exclude the harness this
runbook recommends.

**Decision: enable both.** The witness pins both kinds
(`TRACE_COMMONS_WITNESS_MODEL_KEY_PINS`,
`TRACE_COMMONS_WITNESS_GATEWAY_RECEIPT_KEY_PINS`), each verified only
against its own attested key.

**The accepted cost:** a gateway receipt's signed text is two-part and
names no model, and the gateway key is shared across all hosted models. A
gateway-attested exchange therefore proves the request and response BYTES
and does not prove which model served them — a contributor with a genuine
gateway receipt for a cheap model can declare it as any other model and
both ends accept it.

**Follow-up owed before attested inference feeds credit:** carry
`signature_kind` through to scoring so a gateway-attested trace is
distinguishable downstream. The distinction exists on the wire now;
preserving it is cheap while nothing depends on it and expensive after.
Not a 0.10 blocker — attested inference does not feed credit yet.

### The rollout is three steps, and it reverses today's state

There is no safe two-step order for a pinning deployment: an old witness
refuses a new client (`deny_unknown_fields` on the new `signature_kind`),
and a new pinning witness refuses an old client (absent kind reads as
`Unrecognised`, resolving to an empty key set).

1. Deploy the new witness with **both pin variables unset** — dormant, and
   able to read `signature_kind` without enforcing on it.
2. Ship the 0.10 clients.
3. Set the pins.

Steps 1 and 3 are separate deployments, so each moves the measurement and
needs the pilot pin updated and re-allowlisted.

**This reverses the current state:** production has model pins set from an
earlier deploy and must be UNSET before 0.10 clients ship. Task 4 was
written when enabling the pin was one step; re-read it against this.
