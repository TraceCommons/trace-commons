# Release 0.12 Plan

> **For agentic workers:** steps use checkbox (`- [ ]`) syntax for tracking.
> Read the whole document before starting. The ordering constraints are the
> point; several steps fail silently if taken out of turn.

**Goal:** Ship 0.12 — the release that makes contribution possible without an
invite.

**What 0.12 is:** a person who has never been invited can sign up against a
commons from a shipped application, prepare a receipt-bound session, and
contribute. Every session row now also says whether it carries a checkable copy
of the model call that produced it — a statement about the recording, not about
standing, so it appears for invited contributors too.

**Spec/plan lineage:** `docs/operator/invite-free-admission.md` is the operator
procedure for the headline feature; `docs/operator/near-native-provisioning.md`
covers the signup half.

---

## What gates this release

**Nothing is outstanding on the version bump.** Unlike 0.10 and 0.11, the
version is already in place — #769 bumped all three release crates to `0.12.0`,
the flatpak metainfo already carries a `0.12.0` release block, and both
lockfiles already agree. Step 3 of the 0.11 plan is, this time, a verification
rather than an edit.

What gates it is the invite-free chain working end to end on a real client, and
the four target binaries building.

## Step 0 — Verify the version, do not bump it

This step exists because the 0.11 plan's Step 3 said *"Workspace and crate
versions 0.10.0 → 0.11.0"*, and **that sentence is wrong in a way that wastes
time or does damage.**

**There is no workspace version.** Root `Cargo.toml`'s `[workspace.package]`
holds `edition`, `rust-version`, `license` and `repository` — and no `version`
key. Someone following the old wording will either hunt for a bump that does not
exist or, worse, add one.

Exactly **three** crates carry the release version:

| Crate | Where |
|---|---|
| `trace-commons-contributor` | main workspace |
| `trace-commons-contributor-ffi` | main workspace |
| `trace-commons-contributor-gtk` | **its own workspace**, with its own lockfile |

The other eight main-workspace members (`-attestation`, `-build-info`,
`-gate-api`, `-gate-enclave`, `-mark`, `-operator-client`, `-protocol`,
`-server`) are independently pinned at `0.1.0` and are **not on the release
line**. Do not bump them to match.

- [ ] All three release crates read `version = "0.12.0"`
- [ ] The eight others still read `0.1.0` — a diff touching them is a mistake
- [ ] `crates/trace-commons-contributor-gtk/flatpak/ai.tracecommons.Contributor.metainfo.xml`
      — newest `<release>` block is `version="0.12.0"`. This is a **separate
      stamp that no crate bump reaches**; it was missed at 0.10 and caught only
      by a pre-tag check
- [ ] Four `[[package]]` entries across the two lockfiles agree: `-contributor`
      and `-contributor-ffi` in root `Cargo.lock`; `-contributor` and
      `-contributor-gtk` in `crates/trace-commons-contributor-gtk/Cargo.lock`
      (`-contributor` is mirrored, which is why it is four entries and not
      three)

> **Do not `sed` the lockfiles on the version string.** Third-party crates sit
> at `0.12.0` too — `block-buffer` and `tiktoken-rs` both do today — so a blind
> `0.12.0` → `0.13.0` replacement corrupts dependency pins silently. Match on
> the `name = "trace-commons-…"` line above each `version`, and check the diff
> line count against the four you expect.

### Sites that correctly hold no version stamp

Several places look like they should carry the version and deliberately do not,
because they derive it at build time. **Do not "fix" these.**

| Site | How it gets the version |
|---|---|
| `macos/scripts/info-plist.sh` | takes `<short_version> <build_version>` as arguments |
| `windows/packaging/Package.appxmanifest` | `Version="0.0.0.0"` placeholder by design |
| `windows/scripts/make-msix.ps1` | stamps at package time |
| `windows/scripts/make-appinstaller.ps1` | stamps at package time |
| `scripts/updates/generate-manifest.sh` | derived |
| `scripts/updates/generate-appcast.sh` | derived |
| `scripts/install.sh`, `scripts/install.ps1` | resolve the newest `contributor-v*` tag |

The install scripts deserve a note: they resolve the newest `contributor-v*`
tag **explicitly**, and not `/releases/latest/download`. This repository
publishes two independent tag streams, so GitHub's "latest release" is whichever
was cut most recently and may hold no CLI assets at all.

## Step 2 — All required checks green

- [ ] **Fourteen** required status checks green, on a branch up to date with

`postgres-suites` is real coverage for the admission path and runs on every PR,
but it is **not** among the fourteen — a red run there needs someone to look,

**The repo is behind a merge queue.** `gh pr merge` only *enqueues*; the required
checks re-run against `main` at merge time and a PR that never receives them
times out of the queue rather than merging. Watch it land; do not assume.

## Step 4 — Tag, in this order

**Push the contributor tag FIRST and wait for its release to exist.** Do not
push both in one command.

`publish-updates` builds `latest.json` by `curl`ing the `contributor-v<version>`
release assets, and **a failed curl is deliberately non-fatal** — the slug is
silently omitted. At 0.9.0 the contributor release finished 107 seconds before
`latest.json` was written. If the app tag runs ahead, a *signed* manifest naming
zero CLI platforms is published, every installed CLI stops seeing updates, and
**no job goes red.**

```bash
git tag contributor-v0.12.0
git push origin contributor-v0.12.0

until gh release view contributor-v0.12.0 --repo TraceCommons/trace-commons \
        --json assets --jq '.assets | length' 2>/dev/null | grep -qE '^[1-9]'; do
  sleep 30
done

git tag app-v0.12.0
git push origin app-v0.12.0
```

- [ ] Contributor tag pushed, release has assets
- [ ] App tag pushed
- [ ] Both workflows watched to completion

- [ ] The desktop family is present as expected too — `generate-manifest.sh`
      knows two deliberately distinct families, the bare `<os>-<arch>` slugs

This is the one failure in the release that does not announce itself. Note the
generator only writes platforms passed on the command line, and refuses to
publish a manifest with none — so the danger is never an empty manifest, it is a
*partial* one that looks fine.

## Known limits shipping in 0.12

State these rather than discovering them in a bug report:

- **An admitted trace is not model-attested.** A verified admission receipt says
  the bytes were produced inside an attested enclave whose signing key we
  pinned. Which model served them is the provider's statement. Do not describe
  an admitted trace as model-attested.
- **Gateway receipts name no model at all**, which is why they are refused
  unless an operator sets `TRACE_COMMONS_ADMISSION_GATEWAY_SIGNERS` on purpose.
- **The WinUI binding layer is only proven by CI.** It does not compile on a
  macOS host, so XAML bindings and converters are verified by the `windows
  contributor app` job and nowhere else.
- **`postgres-suites` does not gate a merge**, so admission-path coverage can go
  red without branch protection stopping anything.
