# Claude agent-branch comparison source profile

Status: reviewed implementation contract; extraction, compatibility tests, and real-file admission remain under implementation. This document does not claim source qualification.

Parent: [personal refactor comparison plan](../plans/2026-09-12-personal-refactor-comparison.md).

## Supported unit and claims

The supported unit is one explicitly imported Claude Code JSONL agent branch. It is structural evidence that the selected branch is internally attributable to one recorded session, one recorded agent, one declared model cohort, and one observed terminal segment. It does not establish that the branch is a whole user task, that its opening `user` record came from a human, that a sibling agent is independent, that the provider served the declared model, or that the work succeeded.

Comparison eligibility remains layered. Structural attribution is necessary, then the existing comparison task still requires user-provided context, a material-bound user outcome, a current independence confirmation, and no frozen overlap. A branch cannot create any of those facts itself.

The first source rule is `ClaudeCodeV2_1_260AgentBranchV1`. The version is descriptive evidence, not the qualification rule. Qualification is the finite record/attachment/state-machine contract below, pinned by named fixtures and structural tests. All records must declare exactly `2.1.260`; unknown writer shapes and versions fail closed.

## Persisted schema and compatibility

Keep `LocalInsight.task_attribution` and its existing Codex evidence struct and JSON unchanged. Add a separate default-omitted `LocalInsight.claude_task_attribution` field containing strictly validated Claude schema-1 evidence. The separate fields provide unambiguous decoding and preserve old serialized bytes. Store validation must reject either field on the wrong source, both fields populated together, a Claude field in a pre-v10 store, or evidence bound to another source digest. Negative compatibility fixtures must cover each case.

The Claude object contains:

- `schema_version`, `extractor_version`, and a fixed source profile (`profile_id`, observed writer version, qualification scope `observed_writer_agent_branch_records`);
- exact `source_digest`, physical `record_count`, and `recognized_records`;
- `root_session_identity_sha256`, domain-separated from the exact recorded session identity;
- `agent_branch_identity_sha256`, domain-separated from the exact ordered `(session identity, agent identity)` pair;
- recorded model evidence: exact assistant declaration, exact model attachment selector, and an optional *recognized* context-window selector. Only the literal terminal `[1m]` form is recognized for this rule. For example, `claude-opus-5[1m]` must cross-check an assistant declaration of `claude-opus-5`, while both original strings remain represented. No general bracket stripping is permitted and neither field is called serving identity. Anthropic documents `opus[1m]` as the one-million-token context selection in its [model configuration reference](https://code.claude.com/docs/en/model-config);
- separate `material_attachment_provenance_sha256` and `comparable_settings_sha256`. The material digest binds every evolving prompt/file/environment/memory reference. The comparable-settings value is optional and remains unavailable unless the adapter qualifies a stable, source-native settings projection;
- a state of `Attributed { branch }` or `Unavailable { typed_reason, physical_line }`;
- an attributed branch with ordered physical references, observed terminal status, tool-pair references, repeated assistant-record references, and attachment references.

Every attachment reference stores only attachment kind, one-based physical line, recognized shape/status, and a canonical digest of the source-native attachment value. Prompt, command, output, file, instruction, environment, memory, and response bodies are never persisted.

Increment the Insights store version. Older snapshots keep `task_attribution = null` or their existing Codex object, omit the new Claude field, and remain unknown for Claude qualification until explicit reimport. Native macOS/Windows/GTK JSON decoders receive compatibility fixtures for old Codex, null legacy Claude, and new Claude; the shared Rust validator remains authoritative rather than duplicating admission logic in shells. Existing Codex frozen-task fields and serialized bytes remain unchanged. Claude root/branch identity fields are appended with `default` plus `skip_serializing_if = empty`, so decoding and reserializing old Codex tasks does not change their material digest, outcome binding, or independence confirmation.

## Exact source-native state machine

Read exact bytes once and count every physical JSONL line. Do not reuse the descriptive parser's display-message deduplication.

1. Every record must be valid JSON with a recognized top-level kind (`user`, `assistant`, or `attachment`) and the exact supported envelope keys/types. Every record must carry the same valid session identity, agent identity, and sidechain state. The initial rule requires an agent branch (`isSidechain == true`). Missing/conflicting identities, a second session or agent, unsupported top-level kinds, and unknown envelope fields are typed unavailable.
2. UUID and parent UUID links must be canonical and internally consistent under a source-native chain rule. Repeated assistant message IDs are permitted and retained as distinct physical records. They are metadata observations from one stream and never counted as independent calls or turns. A repeated ID cannot change session, agent, role, or declared model.
3. Assistant content blocks are processed in physical order. Supported blocks are text, thinking, tool-use, and the source-native result representation observed in user records. Each tool-use ID must be unique and must pair with exactly one later protocol response before terminal `end_turn`; results cannot precede or duplicate calls. A paired protocol response does not generally prove that asynchronous work completed. Snapshot records may repeat exact blocks. Exact `(message ID, block kind, block identity, canonical block digest)` repeats are marked repeated observations; distinct blocks under the same message ID remain distinct and cannot be dropped. Tool names and input/result shapes are allowlisted by the pinned rule. A source-native delegation tool (`Agent`, `Task`, or another observed delegation name) makes attribution unavailable unless a later version links and validates the child branch. This prevents a closed parent call/result from admitting unobserved child-model work as homogeneous. The selected file being a delegated-to sidechain remains supported; delegating further from that branch does not. `Monitor` is an allowed asynchronous source tool, not a synchronous completed operation: its tool result proves only `observed_background_launch`. Persist a domain-separated hashed task-ID reference and `persistent`/timeout status with `async_work_status_unavailable` unless a matching supported stop or completion record is present. A Bash result carrying a background task ID receives the same treatment. Terminal `end_turn` never upgrades either status to process or task completion, and missing future events remain outside selected-file completeness.
4. Exactly one assistant declaration cohort is required. `<synthetic>`, missing, malformed, or mixed declarations are unavailable. The single model attachment must use the recognized shape and must cross-check the declaration under the literal `[1m]` rule above. The attachment is configuration evidence only.
5. Supported attachments are recognized explicitly and retained in order: `model`, `deferred_tools_delta`, `environment`, `skill_listing`, `instructions`, `session_context`, `date`, `agent_listing_delta`, `mcp_instructions_delta`, `auto_mode`, `total_tokens_reminder`, `queued_command`, `hook_success`, `edited_text_file`, and `nested_memory`, each with an exact audited outer key/type shape. Nested bodies are bounded opaque JSON: they are canonically digested and line-referenced, not ignored, retained, or interpreted as policy. This binds payload changes without inventing semantics for opaque fields. The exact source digest also binds byte and formatting changes that canonical JSON projection may normalize. `queued_command` is material attempt/prompt context. Instructions, session context, environment, tool/agent/MCP deltas, auto mode, edited files, and nested memory are material recorded context. `hook_success` is auxiliary hook evidence linked to an existing tool-use ID and never substitutes for a tool result. Token reminders do not become usage evidence. Unknown attachment types/outer shapes are typed unavailable.
6. Qualification requires exactly one final physical assistant record whose `message.stop_reason` is `end_turn`, with null stop sequence and no later user, assistant, queued-command, material configuration, tool call, or result records. All tool calls must already be paired. Persist this as `observed_branch_segment_ended`; never label it task completion or export completeness. `stop_sequence`, missing `end_turn`, multiple terminal records, or later material records are typed unavailable.

The audited envelope uses optional arrays for `rendered` and `renderedInHumanTurn`; their bounded contents are opaque source material, not prompt authorship evidence. The model attachment's `text` field is a string. A ToolSearch protocol response may contain an array of exact `tool_reference` blocks with string `tool_name` fields. Those references describe offered tools, not calls or delegation. Unknown nested result block kinds remain unavailable. `TaskStop` is an allowed stop-request tool with exact native response string fields `command`, `message`, `task_id`, and `task_type`; its name does not make it a delegation tool, and its response does not establish background-work completion.

The material attachment provenance digest covers the ordered canonical projection of every attachment reference, including evolving queued prompts, edited files, environment changes, and memory. The branch material digest covers ordered record references and canonical content digests. Neither retains source bodies. These values bind work evidence and are not used as a same-configuration test across attempts. A separate comparable-settings digest may cover only a reviewed stable adapter projection; it remains unavailable in v1 if the structural audits cannot justify one. Comparison configuration then comes solely from the existing explicit user context.

## Store, overlap, and comparison admission

Frozen episode bindings preserve the existing `source_session_identity_sha256` field exactly and append default-omitted `claude_root_session_identity_sha256` and `claude_agent_branch_identity_sha256` sets. Canonical overlap keeps the existing Codex key unchanged and adds source-qualified Claude keys (`claude_root_session:...`, `claude_agent_branch:...`). Different byte exports of the same Claude branch overlap through both identities. Parent siblings with distinct agent IDs still overlap through the shared root-session identity, so they cannot be admitted as independent tasks merely because their files or agents differ. Preserve already validated identity hashes when model metadata or terminal attribution is unavailable; attribution failure must not erase known overlap evidence.

Source qualification dispatches explicitly on source format and the corresponding validated evidence field; field presence alone cannot select a source rule. Claude qualification requires exact source digest, profile/rule, frozen root and branch identities, attributed state, one consistent declared model cohort, bound material-attachment provenance, and observed branch-segment termination. It does not require evolving work material to have identical digests across branches or attempts. `ComparisonTaskSourceQualification.recorded_configuration_sha256` becomes default-omitted optional data: existing Codex emits the same string bytes, while Claude emits it only if the adapter has a qualified stable settings projection. The existing user-supplied `ComparisonTaskContext.configuration_fingerprint` remains the comparison stratum authority. Claude yields a new `QualifiedSourceRule::ClaudeCodeV2_1_260AgentBranchV1`. It supplies no time, usage, outcome, task context, independence, or background-process completion facts.

The sanitized pilot evidence indicates PR 616 and PR 606 can exercise the supported structural path: one session/agent each, closed tool pairs, one `end_turn`, and the known attachment families. Because they share the root session, frozen comparison tasks containing them must overlap. PR 632 exercises typed unavailability because it has a synthetic declaration and `stop_sequence` without `end_turn`.

## Tests and qualification evidence

Synthetic fixtures cover a qualified branch, repeated assistant IDs with incremental distinct blocks, exact repeated snapshots, missing/mixed/synthetic model labels, recognized `[1m]` selector matching, arbitrary bracket rejection, every supported attachment shape, queued-command materiality, hook/tool-result separation, missing/duplicate/out-of-order tools, nested delegation exclusion, Monitor and background-Bash launches without false runtime or completion claims, identity conflicts, unknown attachments, `end_turn`, `stop_sequence`, and post-terminal records. Store tests cover byte-stable legacy Codex decoding/reserialization and material digests, explicit-reimport behavior, same-branch different-byte overlap, sibling-agent root-session overlap, frozen deletion/reimport behavior, differing evolving material without false configuration conflict, and full comparison eligibility only after existing user gates.

The authorized structural audit covered all three selected files and supplied envelope/attachment shapes, UUID parent ordering, repeated-message envelope identities, terminal ordering, and model selector/declaration cross-checks. Every record declares writer version `2.1.260`. The two candidate branches for #616 and #606 have unique envelope UUIDs, one initial null parent, all remaining parent references earlier in the file, and a final text `end_turn` with no later records. Their model attachment uses the literal recognized `[1m]` selector. The #632 fragment ends with `stop_sequence` and remains unavailable.

The audit found native `Monitor` calls in both candidate branches. Its protocol result represents a background launch, as documented in the [Monitor reference](https://code.claude.com/docs/en/agent-sdk/python#monitor). It does not establish completion of that background work. No source-native `Agent` or `Task` call was observed in these selected branches; opaque shell commands still do not prove absence of external model work or exclusive authorship.

Implement synthetic regressions from these shapes, then run explicit local reimports against the authorized originals. Both #616 and #606 must exercise the supported structural path while retaining shared-root overlap; #632 must retain typed unavailability. An attachment-free or top-level-only synthetic path cannot satisfy this acceptance gate. If a required shape cannot yet be supported, report the milestone incomplete and investigate that shape rather than guessing its semantics. Preserve raw inputs and private audit artifacts locally.
