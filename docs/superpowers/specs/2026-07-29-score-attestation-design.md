# Server-signed score attestations

Date: 2026-07-29
Status: Approved design, pending implementation

## Problem

A submission id is currently a bearer token for credit. `POST
/v1/admin/scores-by-submission` returns `{submission_id,
credit_quality_micros, perplexity_micros, novelty_score_micros,
gate_passed}` with **no contributor identity**, so a collector scoring a
hackathon cannot tell whether the participant who handed over an `ids.json`
actually produced those traces.

This is not hypothetical. The Devfolio feedback page published seven real
submission ids in plain text, including two accepted ones. Anyone with that
link can claim them today.

Querying by contributor instead does not by itself fix it: the only
per-contributor identity, `trace_submissions.auth_principal_ref`, never
leaves the server, and the value that *is* returned to clients at onboarding
(`contributor_label`) hangs off the allowlist entry — per invite code, shared
by every contributor onboarded through an invite with `max_uses > 1`.

A participant asserting their own identifier to the collector reproduces the
original forgery with a different token. The binding has to be something the
participant cannot mint.

## Design

Ingest gains its own Ed25519 signing key and signs a statement of a
contributor's own scores. The participant relays that statement to the
collector, who verifies it against a published keyset. Forging one requires
the ingest signing key.

### Why a separate key from the issuer's

The issuer's key mints upload claims — it carries **write** authority over
the corpus. The attestation key signs read-only statements about scores that
already exist. Reusing the issuer key would mean a collector, an external
party, pins the same trust root that authorizes contribution, and would widen
what an issuer-key compromise buys an attacker.

They are also operationally different: the issuer key lives on the issuer
host and is already deployed; scores live in ingest's database. Signing in
ingest avoids a cross-service signing path where ingest asks the issuer to
attest to data the issuer cannot itself verify.

### Key material and configuration

Mirrors `TraceUploadClaimIssuerConfig` exactly rather than inventing a second
convention:

- `TRACE_COMMONS_INGEST_ATTESTATION_SIGNING_KEY_PEM` — PKCS#8 v2 private key
- `TRACE_COMMONS_INGEST_ATTESTATION_PUBLIC_KEY_PEM` — SPKI public key
- `TRACE_COMMONS_INGEST_ATTESTATION_SIGNING_KID` — key id

Generated by a `--generate-attestation-keypair` subcommand on the ingest
binary, matching `trace-commons-upload-claim-issuer --generate-keypair`
(ring PKCS#8 v2 only; see the pilot's existing key-format constraint).

### Keyset publication

`GET /.well-known/trace-commons-attestation-keyset.json`, returning the same
shape the issuer publishes:

```json
{ "keys": [ { "kid": "...", "public_key_pem": "..." } ] }
```

An array, not a single key, so rotation can publish old and new together.
Rotation procedure: add the new key to the keyset, wait for collectors to
refresh, switch signing to the new kid, then retire the old key. A collector
must select the verifying key by the `kid` in the attestation, never by
position.

### What is attested

A JWS over canonical JSON, `kid` in the header:

```json
{
  "schema_version": "trace_commons.score_attestation.v2",
  "tenant_id": "...",
  "auth_principal_ref": "...",
  "submissions": [
    { "submission_id": "...", "credit_quality_micros": 0,
      "perplexity_micros": 0, "novelty_score_micros": 0,
      "gate_passed": true,
      "coverage": { "coverage_state": "complete",
                    "chunks_scored": 3, "chunks_total": 3 } }
  ],
  "issued_at": "...",
  "expires_at": "...",
  "nonce": "..."
}
```

`coverage` (schema v2) states how much of the trace the scores were computed
over: `complete`, `partial` (with a known `chunks_total`), or
`partial_unknown_total` for a decision recorded before the pre-cap total was
persisted (migration V47). An unknown denominator is reported as unknown and
is never estimated. v1 is no longer issued; see `docs/collector-integration.md`
for the collector-facing migration.

`auth_principal_ref` is included so a collector can detect two participants
relaying attestations for the same contributor. It is already a reference
rather than raw contributor identity; no new identity material is exposed.

### Replay and staleness

`expires_at` is mandatory and short (default 24h, operator-configurable). A
collector must reject an expired attestation and must not cache one past its
expiry. `nonce` lets a collector detect a replayed document within the
validity window.

This does not stop a participant relaying a *valid* attestation for scores
they genuinely earned — that is the intended behavior. It stops a participant
producing an attestation for someone else's.

### Authentication

The endpoint is contributor-authenticated with the caller's existing upload
claim, and returns **only the caller's own** submissions, resolved from the
authenticated principal. It never accepts a principal as a parameter — that
would rebuild the forgery hole one layer up.

### Fail-closed

If the attestation key is not configured, the endpoint returns 503 with the
missing-control label `attestation_signing_key_unconfigured`. It never
returns an unsigned document. Per repo convention, a configured-but-broken
control refuses the path rather than degrading.

### Contributor CLI

`trace-commons-contributor attest --out attestation.json` fetches and writes
the document. This replaces `--manifest` as the artifact a participant hands
to a collector; `--manifest` stays for non-adversarial uses.

## Consequences

- **A second trust root.** Collectors pin the attestation keyset. Losing this
  key means reissuing attestations, not corpus compromise, but it is new key
  material with its own rotation and backup story. It must be added to the
  key-rotation runbook.
- **Ingest gains a signing capability it did not have.** Today ingest only
  verifies (`managed_eddsa_keyset`). Any future review of ingest's blast
  radius has to account for a private key now living there.
- **Attestations are still relayed by the participant.** The design assumes a
  collector who verifies signatures. A collector who accepts an unverified
  document is no better off than with `ids.json`. The verification steps must
  be documented for Devfolio, not left implicit.

## Out of scope

- Binding a contributor to an external identity (a Devfolio handle). That is
  the collector's join, and is better solved by their MCP performing
  enrollment in an authenticated context.
- Proving a participant submitted *all* their traces. Attestations prove
  authorship of what is claimed, not completeness.
- Signing individual submission receipts.
