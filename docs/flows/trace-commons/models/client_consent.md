# Standing consent and approval origins

Source baseline: `8218cc8ae408eb9c2c8a16d5768d9f6e0f7f83d6` in the isolated worktree. Current implemented behavior; only Quint typechecking is authorized. No invariants, temporal properties, selected guarantees or TLC checks are included.

## State and finite identity abstraction

`folders[0..1]` are separate folder policies; `entries[0..1]` are separate queue entries, one per folder. Entry 0 initially waits on disk. Entry 1 initially has not arrived and nondeterministically belongs to a real second folder or the unresolved bucket. `ANewSessionArrives` supplies that second entry, independently of UI selection. The unresolved bucket never becomes automatic even under an Automatic override. These are two session identities, not a model of arbitrary queue sizes or queue eviction.

`grantId` represents the source-listing identity (`granted_at` in source); `generation` represents the independent ordinal used by folder Ask exceptions. Both have two canonical names, 1 and 2. A fresh grant invalidates all old captured source jobs and converts retained old exception references to a stale sentinel before changing names. This is a finite equality/freshness abstraction, **not numeric wraparound of the implementation counter**. Ordinary grants remain possible indefinitely; no artificial maximum generation disables them. Include-existing changes the implementation generation twice within one locked save; only its final fresh equality relation is retained. Numeric overflow, wall-clock ties and timestamp uniqueness are not checked.

`askUnder=-1` means no explicit folder rule; `-2` means a prior explicit Ask. An Ask set under the current generation has its generation name. Keeping existing Ask marks retags configured Ask rules under the fresh include-existing grant; making all folders automatic clears those marks. An old explicit Ask remains explicit under a legacy from-now grant. `byGrant` distinguishes a grant-armed folder from one the contributor armed themselves.

`sourceJob`, `jobId`, `jobCurrent` and per-folder `listingCurrent` capture a listing before disk discovery. Regranting or changing roots invalidates its relevant equality references. A listing for the previous grant cannot record the replacement. Per-folder `recorded/heldPath` distinguish unrecorded from-now holds from a recorded backlog. `projectAtGrant` distinguishes a previously existing project from a new project under legacy grants. `onDisk` represents the two entries' retained pre-grant/history relation; filesystem paths and multiple successive source identities are symbolic. Root 0/1 are canonical identities; each root change invalidates captures rather than allowing equality aliasing.

The queue projection keeps Pending, Approved, Uploading, Uploaded and Refused. Other queue states, retries, receipt history, immutable envelope byte identities and undo deadlines are owned by `client_contribution`, not duplicated here. `origin` is manual/automatic/none, while `scopeOk`, `inputOk`, `pin` and `hold` describe approval drift. Build identity and uploader candidate/retraction identity remain separate from selected folder. Every background row action chooses entry 0 or 1 independently.

## Ordering and abstraction limits

Successful folder changes group policy/save/queue mutation under the source's policy-before-queue ordering. Folder arming's audit unlock/relock, durable-policy versus queue-save partial failures, full settings persistence failures, void-notice acknowledgement IDs and legacy migration are not materialized. They cannot support guarantees about crash durability or exactly-once notices. The grant audit/save path is split because its pre-save failures determine whether a grant is armed; its rollback preserves the previous grant. `audit` is evidence that the append succeeded, not an assertion about audit security or accountability.

The scope-adoption step has no numeric scope set because both initial grant construction and explicit adoption cover the currently chosen list; it exposes config-before/after ordering and invalidates row fingerprints on successful write. Emptying scopes, malformed input variants and exact scope-name validation remain bounded interface outcomes in the source rather than fully enumerated records here. Build-current is conservatively invalidated on any successful scope/config mutation rather than hashing detailed field subsets.

Automatic gate success, privacy/witness evidence, pin persistence, enrollment and capabilities are external validated outcomes supplied by adjacent contribution/identity models. `TheWatcherApprovesAnEligibleEntry` represents the successful automatic gate branch; cryptography, scrubber quality, witness availability and attestation soundness are not proved. Manual Scrub-check retraction, per-session Keep/dismiss/expiry and grouped subagent behavior remain in `client_contribution` or outside this slice. First-run projects and past sessions are bounded to one chosen Ask folder; this model does not implement the complete six-screen first-run UI.

`TheUploaderSnapshotsAnEligibleApproval` represents the policy eligibility stage; folder/global changes may interleave before claim. Queued folder/global actions synchronously retract rows according to their origins; claimed Uploading rows survive those changes. A pass interruption/restart releases Uploading back to Approved, after which the next policy recheck may return/refuse automatic rows. Scope mismatch is checked before claim; changed envelope-input fingerprint is checked after claim and returns a held Pending row. No unconditional stutter action is present. Real source scans/root changes remain world events, with no fairness or eventual-success assumption.
