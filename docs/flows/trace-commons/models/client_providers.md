# Provider accounts and managed configuration

Current implementation projection at `8218cc8ae408eb9c2c8a16d5768d9f6e0f7f83d6`, native macOS plus shared daemon. This is a refinement of the explicitly coarse saved-account/provider interfaces in [client_services.md](client_services.md). It does not replace that model's organization-key ceremony, contribution account, balance or session collection detail. No product promises have been selected; there are no invariants, temporal properties, guarantee tests or TLC results.

## State and finite bounds

Two symbolic saved-account names (`Personal`, `Work`), two provider/tool families (`Claude`, `Codex`) and two session row names expose concurrent accounts and sessions. The provider names denote the native tool/login families from `managed::ToolId` and subscription-usage `Provider`, not an assertion that Claude is the backend serving a NEAR AI session. The connection kind is independent: saved subscription, saved API key, saved NEAR AI key, or derived NEAR AI sign-in. Derived sign-in entries are never saved, renamed or removed as saved accounts. They are projected through the connection selector rather than consuming a saved-account slot.

The single record separates saved metadata/auth hints/credential-store presence, per-tool default and generation, displayed generation, selected UI account, one managed operation and its delayed callback, captured launch request, each session, saved folder preferences, draft folder/catalogue tokens, CLI options sent/stored/acknowledged, one subscription usage claim, listener exposure, held harness plan and configuration-file generation. Two folders (`home`, `project`) and one symbolic nondefault model represent identity/equality rather than real paths or model quality. Background model, collection, fallback preservation and favorite membership remain independent bits.

Five reusable generation names have no ordering. Fresh generations exclude the current and retained request/claim tokens relevant to the operation. Saved-account incarnation excludes the pending prepare identity, so removing/readding a finite account name cannot turn an old prepare into a request for a new UUID. Historical session rows can be dismissed and reused; a row name with pending terminal/proxy work or an outstanding proxy is retained until that work answers/cleans up. These finite identities do not represent an unbounded callback or history archive. Sign-out, removal and window closure have no numeric-cap guard.

`providers_runtime`, `providers_home` and `providers_closed` are internal abstraction panels, not proposed application screens. World actions do not consult the selected frame; in-flight replies, native tools, credential loss and lifecycle sweeps can continue after navigation or closure. Every `You*` action requires its named control in the current frame, with exact screen/phase guards where controls are shared. Runtime navigation/account selectors/sign-out/options/usage controls are explicitly internal panel events; they cannot escape a modal. Automatic reads and callback application use world actions. Explicit refresh requests may return unchanged data; there is no universal wait/stutter action.

## Deliberate abstractions and remaining boundaries

OpenCode is outside the two-family bound. Its absence is not a parity claim: source `managed/accounts.rs:146-153` forbids its subscription accounts; `managed/sessions.rs:1015-1034` requires a named model for saved-key coding sessions, and profile/project isolation differs. The three-family platform catalogue and OpenCode-specific model validation remain explicit coarse interfaces, rather than pretending the Claude/Codex instances exhaust every tool branch. Windows/GTK/Tauri capability, terminal and UI differences are not established by this macOS reference projection.

OAuth/native CLI login, keychain/OS credential reads, tool version probing, folder existence/canonicalization, CLI grammar, exact model catalogue/tier membership, model routing policy, funds, network reachability and disk errors are abstract external outcomes. The model does not execute those effects. It does not model secret bytes, exact file paths, process identity, real-time 45-second lease/120-second ticket duration, collector throttling/concurrency, usage amounts, launch request replay, conversation/resume/start-again ownership, process-tree collection, stuck-row dismissal eligibility, installed terminal choice or unbounded session history. Existing `client_services` supplies broader managed lifecycle/collection composition hooks; these detailed omissions are not proven by that separate model.

The source's current guards are retained unevenly where they are uneven in implementation: token-guarded folder/catalogue/usage results are distinct from ungated managed/harness callback application and proxy-start completion. Do not infer a promise from this comparison. There are no fairness assumptions and no reachability, deadlock, safety or progress result.

## Composition hooks and validation

`YouSaveNewAccount` / credential continuation export saved-account existence and independent credential readiness. `YouMakeAccountDefault` / `AnotherClientChangesDefault` export per-tool selection generation. `YouRequestManagedLaunch` / `TheBalanceReadAnswers` / `TheDaemonPreparesCodingSession` / preference save export captured identity, current-generation check and durable starting session. Redemption/proxy start/running/exit are distinct effects; ticket expiry, non-sign-in unknown lease and subsequent sign-in-loss cleanup must not collapse into UI sign-out. Harness exposure/plan/commit and stored/acknowledged CLI options are separate interfaces.
